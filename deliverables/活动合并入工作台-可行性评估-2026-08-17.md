# 活动合并入工作台 — 可行性评估

> 评估日期：2026-08-17 ｜ 评估范围：前端（`CS-Web-Frontend`）+ 后端（`CS-Web-Backend`）｜ 类型：纯只读分析，未改动任何代码

## 0. 背景与目标

用户提出评估「活动」是否可以合并入「工作台」。经检索代码与文档，确认本仓库「活动」与「工作台」是两个职责截然不同的业务域：

- **活动（Events）**：社团对外的内容门户，公开可访问。
- **工作台（Workbench）**：登录用户的个人工具聚合区，挂在 `/tools` 页顶部。

「合并」有歧义，本报告对三种常见理解分别评估，并给出推荐结论。

---

## 1. 现状速览（事实依据）

| 维度 | 活动（Events） | 工作台（Workbench） |
|------|----------------|---------------------|
| 入口 | 独立路由 `/events` + 子路由 `/events/[id]` | 非独立页，内嵌于 `/tools` 顶部（`src/app/tools/page.tsx:230` `<Workbench/>`） |
| 导航栏 | 顶级项 `/events`（`navbar.tsx:22`，**无需登录**） | 顶级项 `/tools`（`navbar.tsx:23`，**需登录** `requireAuth`） |
| 可见性分组 | `page` 组，key=`events`，`guest:true/member:true/admin:true` | `page` 组，key=`tools`，`guest:false`；widget 为 `wb-*` 组 |
| 前端组件 | `src/modules/events/`（types + ui：card/filter-bar/status-badge/month-calendar/year-accordion-timeline）；管理面板复用 `src/modules/admin/ui/admin-events-panel.tsx` | `src/modules/workbench/`（widget-registry 驱动 7 个 widget + 学习助手视图） |
| 页面 Tab | 时间轴/日历、加入我们、活动管理（仅 admin） | 工作台 / 学习助手（InlineTabs）；widget 显隐（localStorage `wb_widget_prefs`） |
| 后端 API | `events.py`（列表/详情/报名/取消/我的报名）+ `admin_events.py`（CRUD/批量/签到/自定义报名表单/统计/设置） | `workbench.py`（GitHub 热力图 / 番茄钟记录与统计 / LLM 用量与配置 / API 调用统计） |
| 数据模型 | `events→registrations→checkins`（4 张表，含报名/签到链） | `focus_sessions` / `llm_usage` / `llm_config` / `api_call_logs` 等个人统计表 |
| 数据存储 | 后端 PostgreSQL（权威源） | 本地 localStorage 为主；仅 GitHub/考试/LLM 少量走后端 |
| 跨域耦合 | 与 workbench **零共享**（无共同 service/repo/表） | 同左 |

**关键事实**：后端 `workbench` 与 `events` 无任何服务/仓储/表耦合；前端两域组件互不引用。技术上"合并"没有依赖障碍，本质是**产品与信息架构决策**。

**已有聚合先例**：个人主页 `/profile` 的「活动记录」Tab（`src/app/profile/activity-tab.tsx`）已聚合"我的活动"——但仅展示**历史参与记录**，不含报名入口、进行中活动或日历。

---

## 2. 核心矛盾（为什么"整体合并"不成立）

1. **权限模型冲突（最致命）**：活动是**公开内容页**（社团门面，访客可见）；工作台在**需登录**的 `/tools`。整体合并将使访客无法看到活动，除非放开 `/tools` 匿名访问（违背工作台"个人化"定位）。
2. **语义错位**：活动 = 浏览型内容（时间轴/日历/详情/报名），面向所有人；工作台 = 个人工具（待办/便签/番茄钟/统计）。"活动"不是"工具"。
3. **交互深度不匹配**：活动管理含 CRUD、批量操作、签到、自定义报名表单、统计、设置——属重型功能；widget 模型是轻展示卡片（`slot: full/main/side` + 显隐开关），无法承载完整管理。
4. **导航依赖**：`/events` 是导航栏独立项，承担对外曝光与 SEO 入口，删除即丢失首屏曝光。

---

## 3. 三种合并方案评估

### 方案 A：入口聚合（推荐）— 保留 /events，工作台新增「活动」widget

**含义**：`/events` 公开页与导航不动；在 `/tools` 工作台新增一个活动 widget，展示近期/进行中活动 + 我的报名 + 一键报名入口（跳转 `/events`）。这是**聚合**而非**合并**。

**可行性：高 ✅**
- 完全契合现有「registry 驱动」范式：三步（`widget-registry.ts` 声明 → 组装 `widgets/events-overview.tsx` → 注册），复用 `/api/events?status=upcoming` 与 `/api/events/me/registered`（端点已存在）。
- 新增 `wb-events` 可见性 key，纳入 `feature-visibility` 注册表，admin 可开关。

**工作量：M（中等，约 1 个 widget + 1 条 i18n + 1 条可见性注册）**

**风险：低**
- 注意与 `/profile` 活动记录 Tab 的重叠：定位区分——工作台 widget = **进行中/即将开始 + 报名入口（即时行动）**；profile = **历史参与记录（回顾）**；`/events` = **完整浏览**。三者互补不冲突。
- 现有 widget 的 `VisibilityGate` 用 `componentKey={id}`（如 `today-tasks`），而注册表 key 为 `wb-today-tasks`，存在 key 不一致导致 wb-* 管控对 widget 实际 fail-open 的隐患；新增 widget 时应一并统一为 `wb-*` 命名。

**收益**：在工作台"一站式"呈现活动入口，提升登录用户的活动参与率；零破坏性、可逆。

---

### 方案 B：整体迁入工作台 — 删除 /events，活动完全移入 /tools

**含义**：删除 `/events` 顶级页与导航项，活动作为工作台一部分（widget 或独立 section）。

**可行性：低 ❌（不推荐）**

**四大冲突**：
1. 权限冲突（见 §2.1）：公开内容 → 需登录区，对外曝光断裂。
2. 交互冲突（见 §2.3）：重型管理功能无法塞进 widget 模型；若保留 `/tools/events` 独立 section，则实为"搬移"而非"合并"，且 `/tools` 需登录使管理端也受限。
3. 导航冲突（见 §2.4）：删导航项即丢曝光；保留子路由则未真正合并。
4. 演进阻碍：活动域在 Roadmap 1.x 仍有功能缺口（活动评价/相册，待办 P2/L4·L5），保持独立域更利于后续扩展。

**工作量：L（高）**：路由迁移、权限模型改造、widget 化或 section 重构、导航重构、i18n 重组、可见性重新登记、回归测试。

**收益：低**：仅减少一个导航项与一个 `page` 组可见性 key。

**风险：高**：公开性丢失、信息架构混乱、回归风险高、且未来活动扩展被迫挤进工作台。

---

### 方案 C：仅导航收编 — 路由保留，导航栏去掉「活动」入口

**含义**：`/events` 路由与页面保留，但导航栏 `NAV_LINKS` 删除 `/events`；入口改由工作台/工具卡片跳达（新增一个 `visibilityKey='events'` 的工具卡片）。

**可行性：中**
- 实现简单：`navbar.tsx` 删一行 + `/tools` 工具卡片加一项（复用现有工具卡片机制）。

**工作量：S~M（低到中）**

**风险：低（纯 UI/导航调整）**
- 但**公开性名义保留、实际变弱**：访客进入站点后首屏看不到活动入口，仅能凭 URL 直达 `/events`。活动曝光与 SEO 下降。
- 可与方案 A 叠加：导航收编 + 工作台 widget 并存（入口两处都有，抵消曝光损失）。

**收益**：导航栏项减少，信息架构更"聚拢"；若叠加方案 A 则无损。

---

## 4. 综合结论与推荐

| 方案 | 可行性 | 工作量 | 风险 | 收益 | 推荐度 |
|------|--------|--------|------|------|--------|
| A 入口聚合（工作台加 widget） | 高 | M | 低 | 中（提升参与率） | ⭐⭐⭐ 推荐 |
| B 整体迁入 | 低 | L | 高 | 低 | ✗ 不推荐 |
| C 仅导航收编 | 中 | S~M | 低 | 低（减导航项） | △ 可叠加，需权衡曝光 |

**结论**：
- **不建议方案 B（整体合并）**——收益低、风险高，且破坏"活动作为公开社团门面"的产品定位。
- **推荐方案 A** 作为主路径：在工作台新增活动聚合 widget，保持 `/events` 公开页与导航不变。这是符合本仓库 widget-registry 设计哲学、零破坏、可逆的演进。
- 若业务方确想减少导航项，可**叠加方案 C**（导航收编），但必须用方案 A 的 widget 弥补曝光损失，避免活动入口变浅。

---

## 5. 若采纳方案 A 的落地建议（供后续执行）

1. 新增 `src/modules/workbench/widgets/events-overview.tsx`：
   - 调用 `GET /api/events?status=upcoming&pageSize=5` 取进行中/即将开始；
   - 调用 `GET /api/events/me/registered` 取我的报名（未登录时折叠该段）；
   - 卡片内"查看全部"→ `/events`，单条 → `/events/[id]`。
2. `widget-registry.ts` 声明 `{ id:'events-overview', titleKey:'eventsOverview', component: EventsOverview, slot:'main' }`。
3. `registry.ts`（feature-visibility）补 `{ key:'wb-events-overview', group:'workbench', ...default:{guest:true,...} }`，并在 `workbench.tsx` 的 `VisibilityGate` 统一使用 `wb-` 前缀 key（顺手修复现有 key 不一致）。
4. `src/i18n/messages/workbench.ts`（或 events 命名空间）补对应词条。
5. 回归：确认与 `/profile` 活动记录 Tab 不重复、访客态 widget 优雅降级。
