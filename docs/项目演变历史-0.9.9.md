### 1. 核心模块评估

#### 模块一：第三方平台贡献热力图（GitHub + LeetCode）

**价值：★★★★★　可行性：GitHub ★★★★★ / LeetCode ★★★☆☆**

- **数据获取**
  - *GitHub*：复用现有 GitHub OAuth 的 access token，后端调用官方 GraphQL `contributionsCollection.contributionCalendar`（一次请求拿全年 365 天数据）。需在 OAuth scope 中确认包含 `read:user`。
  - *LeetCode*：无官方公开 API。可行路径是 `leetcode.cn/graphql` 的 `userCalendar` 查询（公开资料仅需用户名，无需登录），或让用户手动填 Cookie 提升稳定性。**这是全方案最脆弱的一环**，必须做熔断降级：接口失败时展示最近一次缓存 + 「数据更新于 X 前」提示。
- **展示形式**：两张 53×7 的方格热力图（CSS Grid 手写，约 80 行代码，无需图表库），配色复用现有 CSS 变量体系（绿阶），hover tooltip 显示日期+次数，右侧附「近一年总提交/刷题数、当前连续天数、最长连续」三个数字徽章。LeetCode 卡片额外提供「绑定用户名」入口。
- **更新频率**：热力图是低频数据，**后端每 6 小时抓取一次**（复用 asyncio 后台循环），结果落库缓存（新表 `contribution_cache`）。前端只读缓存，SWR `refreshInterval: 5min` 或干脆不轮询。绝不让前端直连第三方——避免 CORS、token 泄露和限流。
- **技术难点**：GitHub token 过期/用户撤销授权 → 抓取失败时保留旧数据并在卡片角落标注「授权失效，请重新连接 GitHub」；LeetCode 端点变动 → 抓取逻辑隔离成独立 service，失败自动熔断 + 指数退避。

#### 模块二：时间信息（当前时间 + 会话在线时长）

**价值：★★★☆☆　可行性：★★★★★（半天工作量）**

- 纯前端模块，零后端依赖。当前时间用 `setInterval(1s)`；会话开始时间写 `sessionStorage`（新开标签页重置、刷新保留），在线时长 = now - start。
- 建议扩展为「问候条」：按时段显示「早上好/下午好/晚上好 + 用户名」，把时间、日期、星期、在线时长整合成页面顶部的欢迎区，顺带承担工作台的个人化氛围。
- 难点几乎没有，注意组件卸载时 clearInterval，以及 next-intl 的日期本地化格式。

#### 模块三：番茄钟

**价值：★★★★☆　可行性：★★★★★（第一期纯前端即可上线）**

- 第一期：纯前端实现，配置（工作 25min / 短休 5min / 长休 15min / 长休间隔 4 轮）存 localStorage；计时状态也持久化，**刷新页面不丢进度**；状态提示用标题栏闪烁 `document.title = "🍅 休息中"` + 页面内状态色环，不做浏览器 Notification（权限弹窗体验差，可选增强）。
- 第二期：专注记录落后端（新表 `focus_sessions`：开始/结束/时长/是否完成/关联任务），为「周专注时长统计」供数——这让番茄钟从玩具变成数据资产。
- 难点：浏览器 tab 休眠时 `setInterval` 不准 → 用「目标时间戳 - Date.now()」而非倒数计数，从根上免疫休眠漂移；声音提示用 WebAudio 合成，不引外部音频文件。

#### 模块四：学习助手 API 调用统计

**价值：★★★★☆　可行性：★★★★☆（需后端新建埋点）**

- **埋点**：新建 `api_call_logs` 表（user_id、endpoint、method、status、latency_ms、created_at），用 FastAPI 中间件统一记录，不只覆盖 Auxilio——全站 API 都有了可观测性，一石二鸟。
- **聚合**：新建 `/api/v1/stats/api-usage` 接口，返回今日调用数、近 7/30 天按日聚合、按 endpoint 分布。查询频率低但数据量会涨，**用每日预聚合 rollup 表**（复用后台循环每天凌晨跑），避免每次现算大表。
- **展示**：今日调用计数器（大数字卡片）+ 近 30 天调用趋势（手写 SVG 折线/柱状，单系列数据手写成本远低于引入 echarts）+ Top 5 接口占比（水平条形，纯 CSS 宽度即可）。
- **难点**：高并发下中间件写库开销 → 异步 fire-and-forget 写入，失败不影响主请求；rollup 任务失败要有重试。

### 3. 布局与信息层级设计

**设计原则**：从「工具陈列架」变成「信息仪表盘」——用户打开 3 秒内回答三个问题：*今天要干什么？我最近在坚持吗？现在该专注还是休息？*

#### PC 端（≥1024px）：12 列网格

```
┌──────────────────────────────────────────────────────┐
│  问候条：早上好，{name} · 08-08 周六 · 在线 32min      │  ← 全宽，模块二
├──────────────────────────────┬───────────────────────┤
│  ⚠ 今日任务（逾期标红置顶）    │  🍅 番茄钟              │  ← 左 8 列 / 右 4 列
│  （模块：今日聚合）            │  （模块三）             │
├──────────────────────────────┤  ⏳ 考试倒计时          │
│  GitHub 热力图（近一年）       │  📝 快捷便签            │
├──────────────────────────────┤  ─────────────         │
│  LeetCode 热力图（近一年）     │  📊 今日 API 调用：N    │
├──────────────────────────────┤     （计数器卡片）       │
│  API 调用趋势图（30 天）       │  🎯 薄弱知识点 Top3     │
├──────────────────────────────┴───────────────────────┤
│  原工具入口收编为底部「全部工具」紧凑网格                │
└──────────────────────────────────────────────────────┘
```

- **层级逻辑**：第一屏 = 行动（任务 + 番茄钟）；第二屏 = 坚持（热力图）；第三屏 = 复盘（统计趋势）。原有工具卡片入口不删除，收编到底部保持可发现性，老用户无迁移成本。
- **移动端（<768px）**：单列堆叠，顺序即优先级：问候条 → 今日任务 → 番茄钟 → 倒计时 → 热力图（横向可滚动）→ 统计 → 便签。
- **工程实现**：建一个 `widget-registry.ts`（模块 id → 组件 + 默认位置 + 所需数据 hook），页面按注册表渲染；后期加「自定义排序/显隐」时只需把顺序配置存用户偏好，骨架不用动。

### 4. 潜在技术难点与应对总览

| 难点 | 风险 | 应对 |
|---|---|---|
| LeetCode 无官方 API | 端点随时可能变动/加验证 | 独立 service 隔离 + 熔断 + 缓存兜底 + 失败时明示「数据非实时」，不让整页报错 |
| GitHub token 安全与失效 | token 泄露或用户撤销授权 | token 只在后端使用、不落前端；抓取失败保留旧数据 + 重新授权引导 |
| 热力图性能 | 2 张 × 365 格渲染 | 纯 CSS Grid 无压力；数据后端缓存，前端不做聚合计算 |
| API 统计写库开销 | 高频请求拖慢主流程 | 中间件异步写入 + 每日 rollup 预聚合，查询只打小表 |
| 实时性的伪需求 | 有人会觉得「越实时越好」 | 明确各模块刷新策略：时钟 1s（本地）、番茄钟本地、热力图 6h、统计 5min 轮询——**不做 WebSocket**，当前数据密度用 SWR 轮询完全够 |
| i18n 与角色可见性 | 新模块文案、管理员模块泄漏 | 词条随模块同步补 zh/en；系统状态模块前端按 RBAC 角色条件渲染、后端接口同样鉴权 |

### 5. 分阶段改造路线

#### Phase 1：骨架 + 纯前端快赢（约 1 周）
- 搭建 widget-registry 骨架与新布局（问候条、左右分栏、移动端单列）

#### Phase 2：数据化（约 1~1.5 周）
- GitHub 热力图：后端 service + GraphQL 抓取 + `contribution_cache` 缓存表 + 6h 定时刷新

#### Phase 3：补全 + 个性化（约 1 周）
- LeetCode 热力图（含绑定用户名流程、熔断降级）
- 番茄钟二期：专注记录落库、周专注统计

#### Phase 4：纵深（按需）
- 每周复盘卡、系统状态角标（管理员）、浏览器 Notification 可选增强、数据导出

#### 优先级排序（按「价值 ÷ 成本」）
1. 今日任务聚合（价值最高、成本最低，定义工作台灵魂）
2. 时间问候条 + 番茄钟（纯前端快赢）
3. GitHub 热力图（OAuth 现成，视觉冲击力最强）

### 6. 扩展方向 A：学习助手 LLM 化（类网页 LLM 工作台）

#### 6.1 目标形态

首页升级为「学习助手｜工作台」：主区域是类 ChatGPT 的对话界面，副区域承载信息模块。学习助手从「规则引擎 MVP」升级为「LLM Agent」——既能闲聊、答疑，也能调用项目内现有能力（薄弱点分析、任务、资源库、考试倒计时、统计数据）。

#### 6.2 后端架构（新增）

```
前端 /tools/auxilio（对话 UI）
   │  fetch POST /api/v1/auxilio/chat（SSE 流式）
   ▼
FastAPI 路由
   │ ① 鉴权（JWT）② 查询会话上下文（conversations/messages 表）
   ▼
AuxilioAgentService（新建）
   │ ③ 组装 system prompt（注入 analyze_learning_profile 的学习画像 + 用户信息）
   │ ④ 调 LLM（OpenAI 兼容协议，httpx 流式，供应商可配置）
   │    └── 收到 tool_calls → 查工具注册表 → 执行 → 结果回传 → 继续生成
   │ ⑤ 落库消息 + 写 api_call_logs 埋点（token/延迟/状态，喂给统计模块）
   ▼
StreamingResponse（SSE：data: {delta} / {tool_call} / {done}）
```

**关键技术决策**

| 决策点 | 选择 | 理由 |
|---|---|---|
| LLM 协议 | OpenAI 兼容 `/chat/completions` + `stream: true` | 一套实现通吃 DeepSeek/通义/Kimi/OpenAI/本地 vLLM，`httpx` 已有依赖，无需新增 SDK |
| 配置 | Settings 新增 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` / `LLM_TIMEOUT` | 沿用现有 pydantic-settings + `.env` 模式，密钥不落库不落前端 |
| 流式 | SSE（`text/event-stream`） | 打字机效果体验最好；Next route handler 已做过 `/api` 代理，透传即可 |
| 会话持久化 | 新表 `conversations`（id, user_id, title, created_at）+ `messages`（id, conv_id, role, content, tool_calls, created_at） | 支持历史会话列表 + 上下文续聊；也是 API 统计的旁证数据 |
| Skills（工具调用） | 工具注册表：`dict[str, Callable]` + 每个工具一个 schema | LLM 走原生 `tool_calls`，后端执行后回传，标准 agent 循环 |

**首批 Skills（全部复用现有能力，零新数据源）**

| Skill 名 | 后端实现 | 数据来源 |
|---|---|---|
| `analyze_learning_profile` | 直接调现有 `AuxilioService.analyze_learning_profile` | 现有弱项分析 |
| `get_exam_countdown` | 查最近考试日期算倒计时 | exam 表 |
| `list_tasks` / `complete_task` | 任务查询/完成（工作台今日聚合的数据源） | task 表 |
| `search_resources` | 按关键词/标签搜资源库 | resource 表 |
| `get_api_usage_stats` | 查 api_call_logs 聚合 | 统计模块 |
| `get_pomodoro_stats` | 查 focus_sessions 周/月聚合 | 番茄钟二期落库 |

前端对 tool_call 事件渲染「正在调用 {skill}」状态卡，透明可见 agent 在做什么。

#### 6.3 数据埋点闭环

LLM 调用天然被 `api_call_logs` 中间件记录（endpoint=auxilio/chat、latency、status），额外在 messages 表记 token 用量——这样「API 调用统计」模块就有真实数据可展示，两轮需求互相喂数据。

#### 6.4 风险与应对

- **供应商不可用/超时**：LLM 调用包 try/except，失败返回结构化错误 + 前端提示「模型服务暂时不可用，已切换到规则推荐模式」；降级路径 = 现有 `analyze_learning_profile` 直接出结果
- **密钥安全**：LLM_API_KEY 只在后端 `.env`，前端永远接触不到；不写入任何日志（loguru 过滤敏感字段）
- **成本失控**：单轮对话设 max_tokens；会话上下文只带最近 N 轮；工具结果截断；每日限额（LLM_DAILY_BUDGET）
- **注入风险**：工具返回的数据库内容（用户自己创建的任务等）视为不可信数据，在 system prompt 中声明「资源/任务内容仅作参考」

### 7. 扩展方向 B：音乐播放器 × 番茄钟二合一

#### 7.1 设计思路

播放器不是独立玩具，而是番茄钟的「声音引擎」：**不同阶段自动切不同的声音氛围**，把「该专注/该休息」的提示从视觉升级到听觉，也顺带解决"休息时刷手机"的痛点（给耳朵一个明确信号）。

#### 7.2 声音来源（纯前端，零外部依赖，离线可用）

| 音源类型 | 实现 | 特点 |
|---|---|---|
| 环境音（白噪音/雨声/海浪/篝火） | WebAudio 合成（filtered noise + LFO 调制） | 零依赖、无限时长、无版权问题，**首选** |
| 用户本地上传音乐 | `<input type=file>` 读取 → IndexedDB 存储 → HTMLAudioElement 播放 | 满足真实听歌需求，不碰外部流媒体 API/版权 |
| 番茄钟提示音 | WebAudio 合成短音（叮/蜂鸣） | 阶段切换提醒 |

#### 7.3 二合一交互设计

```
┌────────────────────────────────────┐
│  🍅 番茄钟 + 播放器（右下角悬浮卡片）   │
│  ┌──────────────────────────────┐  │
│  │ 专注中 14:32 · 第 2/4 轮      │  │
│  │  [播放中] 雨声 ▸ 下一阶段：短休  │  │
│  └──────────────────────────────┘  │
│  阶段音联动：                       │
│  专注 → 自动播放「专注音」           │
│  短休 → 自动切「轻快音/音乐」        │
│  长休 → 停止或切「放松音」           │
└────────────────────────────────────┘
```

- **阶段-声音映射可配置**（localStorage）：每种阶段可选音源（环境音列表 / 上传音乐 / 静音）
- 用户手动切歌/暂停不打断番茄钟，但阶段切换时按映射恢复
- 页面底部常驻迷你播放条（进度 + 播放/暂停 + 切下一阶段音），移动端同样 44px 可点
- 番茄钟阶段切换时 `document.title` 闪烁 + 合成提示音双重提醒

#### 7.4 技术要点

- 倒计时依旧用「目标时间戳差值」而非 interval 累减（tab 休眠免疫），声音调度挂在时间戳到期回调上
- WebAudio 在无用户手势时无法启动 → 首次点击「开始专注」时创建 AudioContext 并 resume，顺带解决浏览器自动播放策略
- 上传音乐存 IndexedDB（localStorage 5MB 不够放音频），播放器用 IndexedDB + URL.createObjectURL 读取
- 播放器组件与番茄钟组件解耦（各自独立 hook），通过一个轻量 event bus（或组件内共享 state）做阶段联动，方便后期拆分复用

## 二、功能模块可见性管理方案（原 `FeatureModuleVisibility-Plan.md`，规划 2026-08-07，落地 0.9.9）


> 版本：草案 v1（2026-08-07）· 已落地（2026-08-09）· 范围扩展至全组件（2026-08-08）
> 状态：已落地（后端 Schema/路由/2FA/审计 + 前端 BFF/Hook/管理面板/导航改造均完成，并扩展为全组件注册表门控，ts-check/eslint 绿，服务层+审计集成自检通过）
> 范围：CS-Web-Backend + CS-Web-Frontend（monorepo 两个 submodule）
> 目标：root 管理员可在后台管理"功能模块是否对哪类用户展示"，并对每次修改执行**弹窗二次确认 + 2FA 验证**，复用现有代码逻辑，仅对源代码做最小必要改动。

---

### 0. 背景与现状（已通过代码探索核实）

| 维度 | 现状 | 结论 |
|---|---|---|
| 功能模块/菜单 | 前端**硬编码配置数组**（`navbar.tsx` 的 `NAV_LINKS`、各页面 `AdminTab`），后端**无** menu/nav 概念 | 可见性规则需新增后端数据源，前端改为从后端拉取 |
| 可见性过滤维度 | 前端仅两层：`requireAuth`（是否登录）+ `user.role`（admin/root）明文比较 | 需扩展为"未登录 / 已登录 / 管理员"三态规则 |
| 2FA | 后端 `TOTPService.verify(user_id, code)` 完整可用；前端 `useTwoFA` + BFF `/api/auth/2fa/verify` 完整 | **直接复用**，无需新写算法 |
| 二次确认弹窗 | 前端全局 `ConfirmProvider` + `useConfirm()`（danger/warning/info 变体）已就绪 | **直接复用** |
| 审计日志 | 后端 `POST /api/v1/audit/logs`（操作者身份服务端推导、防伪造）+ 前端 BFF `/api/admin/actions/*` | **直接复用**为修改留痕 |
| 站点设置存储 | 后端已有通用 `Setting` 模型（`module`+`key`→JSON `value`） | **直接复用**存储可见性配置 |
| 权限闸门 | BFF `requireRoot(req)` / 后端 `is_superuser` | 配置接口挂 root 守卫 |

**核心结论**：本功能所有"安全/交互/存储"底座均已存在，规划重点是**薄增量层 + 数据流打通**，不重写任何核心逻辑。

### 1. 数据模型设计（复用 `Setting`，零新表）

新增一条设置记录（存于现有 `settings` 表，无需 Alembic 迁移新表）：

```
module = "feature_visibility"
key    = "<功能模块标识，如 tools / community / events / about>"
value  = JSON: {
  "guest":     true/false,   // 未登录是否可见
  "member":    true/false,   // 已登录（普通用户）是否可见
  "admin":     true/false    // 管理员（admin/root）是否可见
}
```

- 全站所有受管模块的配置聚合在 `key` 维度；亦可改用单条 `key="all"` 存整个映射对象，二选一（推荐**按模块多行**，便于缓存与单点更新）。
- 读取走后端已存在的 `Setting` 仓储/服务（确认 `app/services` 是否有 `SettingService`；若无，新增一个轻量读取函数复用 `Setting` 模型与 `get_db`）。

### 2. 后端改动（CS-Web-Backend）

#### 2.1 新增 Schema — `app/schemas/feature_visibility.py`
- `VisibilityRule`（guest/member/admin 三布尔）
- `ModuleVisibility`（module_key + VisibilityRule）
- `FeatureVisibilityConfig`（list[ModuleVisibility]）—— 列表响应
- `UpdateVisibilityRequest`（module_key + VisibilityRule）

#### 2.2 新增路由 — `app/api/v1/admin/feature_visibility.py`
挂在 `/api/v1/admin` 下（与现有 admin 路由一致），全部依赖 `require_root`：

| 方法 | 路径 | 说明 | 守卫 |
|---|---|---|---|
| GET | `/admin/feature-visibility` | 拉取全部模块可见性 | `require_root`（is_superuser） |
| PUT | `/admin/feature-visibility/{module_key}` | 更新单模块可见性 | `require_root` + **2FA 校验** |

> 注意：PUT 接口内部**复用 `TOTPService.verify_or_raise(current_user.id, totp_code)`**（来自 `app/services/totp_service.py`）校验 2FA；请求体含 `totp_code` 字段。**强制 2FA（决策 B）**：落库前先检查 `current_user` 的 2FA 启用状态（读 `TwoFactorAuth.enabled`），未启用即抛 `TWO_FACTOR_NOT_SETUP` 拒绝修改，不允许"未启用直接放行"绕过。

#### 2.3 2FA 校验接入（复用）
在 PUT handler 中注入 `TOTPService`，于落库前调用 `await totp_service.verify_or_raise(current_user.id, body.totp_code)`。验证失败抛 `TOTP_INVALID`，前端弹错。

#### 2.4 审计留痕（复用）
更新成功后**调用 `AuditService.record`**（或 `POST /api/v1/audit/logs`）记录一条：
- `action = "feature_visibility.update"`
- `resource_type = "feature_module"`，`resource_id = module_key`
- `actor` 由服务端从 `current_user` 推导（不信任客户端）
- 详情含新旧规则

#### 2.5 注册路由
在 `app/api/v1/__init__.py` 或 `app/main.py` 的 admin 路由聚合处 `include` 新路由，保持与 `admin/users`、`admin/roles` 一致的前缀风格。

### 5. 安全约束与边界
1. **root 专属**：配置读写均挂 `require_root`（后端 `is_superuser` + BFF `requireRoot` 双闸门）。
2. **2FA 强校验（决策 B）**：PUT 更新必须携带有效 TOTP，且 root **必须已启用 2FA**，否则拒绝（防"未启用直接放行"被绕过）。
3. **审计不可绕过**：所有变更经 `AuditService` 服务端落库，actor 身份服务端推导。
4. **前端降级策略**：可见性配置加载失败/网络异常时，前端**回退到原硬编码规则**（fail-open），避免整站导航消失；但真实权限闸门仍在 BFF/后端，前端隐藏不等于接口不可达（保持现有安全模型）。
5. **无新表迁移风险**：复用 `settings` 表，无需 Alembic 新迁移；但需在种子/初始化中保证默认可见性记录存在（否则首次读为空，触发降级）。
