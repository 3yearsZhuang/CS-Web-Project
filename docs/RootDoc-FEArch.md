## 一、设计哲学（三句话）

1. **内容按「原子 → 有机体」生长**：UI 从最小不可分单元组合出来，而非从页面反向切碎。
2. **目录按「职责 → 模块」收口**：每个目录有且只有一个明确的职责边界。
3. **配置按「单块 → 聚合」暴露，样式按「变量 → 优先级」克制**：配置即数据，样式不靠 `!important` 强权。

项目的可维护性不来自功能多少，而来自**每一次新增都落在既定格子里**。

## 二、内容设计规范（Content Design）

### 2.1 分层即内容（Atomic Design 落地）

内容按四级组织，**绝不按文件后缀**（`.tsx`/`.vue`/`.svelte`/`.ts`）分组。

| 层级 | 定义 | 典型载体 |
|------|------|------|
| **atoms** | 不可再分、无业务逻辑、高度复用 | `Button` `Icon` `Badge` `Chip` `Input` `Card` |
| **molecules** | 2–5 个原子组合，单一交互 | `SearchBar` `Pagination` `DropdownMenu` `FormItem` |
| **organisms** | 复杂业务组合，可含子目录 | `Navbar` `Sidebar` `Footer` `Player/` `Calendar/` |
| **widgets** | 独立功能单元，可配置位置 | `Profile` `Categories` `Tags` `SiteStats` |
| **features** | 特定功能集合（含服务/逻辑） | `comment/` `search/` `auth/` `media/` |

**黄金法则**：写新 UI 前先查现有原子组件；不存在且满足
「重复 ≥ 2 次 / 职责单一 / 可独立存在 / 可配置化」才新建。

### 2.2 内容边界契约

- **展示组件** 与 **容器/管理器** 分离：UI 组件只管渲染，数据获取/状态管理抽到 Hook / store / service
- **同名组件绝不散落多目录**（反例：同一看板娘/播放器组件在 widget/features/pages 各一份）

### 2.3 配置即内容数据

- 每个功能一块独立配置文件，统一 `config/index.ts`(或 `index.ts`) 聚合导出
- 运行时消费的「组件清单 / 功能开关」派生为聚合对象，**配置即数据驱动渲染**
- 配置入口用 ASCII 表 / 注释说明每个导出项

### 2.4 复用阈值（量化红线）

| 信号 | 阈值 | 动作 |
|------|------|------|
| 重复 UI 结构 | ≥ 2 次 | 抽取为原子/分子组件 |
| 组件总行数 | > 500 | 必须拆分 |
| 样式代码 | > 200 行 | 拆出/提取 |
| 逻辑代码 | > 150 行 | 提为 Hook / composable / util |
| 状态变量 | > 10 个 | 拆子组件 + 全局状态 |
| 导入依赖 | > 10 个 | 提取服务层 |

**拆分四法**：按功能 / 按 UI 层级 / 按关注点 / 提取通用容器。

### 2.5 样式内容法则

- **禁用 `!important`**（仅第三方注入样式例外，且须集中、须审批）
- 覆盖优先级链（从高到低尝试）：
  1. 原子类 / 工具类（Tailwind / UnoCSS / 框架原子方案）
  2. 提高选择器特异性
  3. 设计令牌（CSS 变量 / Theme 对象）
  4. 组件作用域样式
  5. 全局样式（谨慎）
  6. `!important`（末位手段）
- 主题切换一律走设计令牌（CSS 变量或 theme provider），不用 `!important` 强刷
- 原子类管布局间距，自定义样式管组件特有行为

### 2.6 接入仪式（防「配置了不显示 / 注册了不生效」）

新增可插拔模块（侧边栏组件、路由、插件、Provider），**声明 → 配置 → 注册 三处缺一不可**：
1. 类型/接口中声明
2. 配置文件中启用并排位
3. 在注册表/渲染器中登记（多入口相互独立，勿只登一处）

## 三、目录设计艺术（Directory Art）

### 3.1 按职责分层，拒绝技术分层

```text
❌ components/tsx/  components/vue/  utils/ts/      ← 按后缀分组（禁止）
✅ components/  features/  utils/  hooks/  types/   ← 按功能分组（采用）
```

### 3.2 标准骨架（框架无关）

```text
src/
├── components/        # {atoms, molecules, organisms, widgets, features, layouts}
├── layouts/           # 页面级骨架
├── pages/ 或 routes/  # 路由（posts/ settings/ api/）
├── config/            # 单职责配置块 + index 聚合
├── hooks/ 或 composables/  # 复用逻辑（按功能）
├── utils/             # *-utils 按功能；types/ 子目录收类型
├── types/             # 集中类型（避免单个巨型文件）
├── stores/ 或 state/  # 全局状态（Pinia / Redux / Svelte store）
├── constants/         # routes / theme / endpoints
├── i18n/              # key 定义 + languages/{zh-Cn,en,...}
├── assets/ 或 public/ # 静态资源
├── styles/            # global / theme / 第三方覆盖
├── services/ 或 api/  # 数据访问层（与组件解耦）
└── plugins/           # 框架插件
```

### 3.3 复杂组件 = 子目录即模块

```text
Player/
├── Player.tsx         # 组合层（< 50 行）
├── MiniPlayer.tsx
├── controls/          # PlayControls / ProgressBar / VolumeControl
├── hooks/             # useAudio / usePlaylist
├── types.ts
└── index.ts           # 桶导出
```

每个复杂组件自带 `hooks/`、`types.ts`、`index.ts` 桶导出 →
「目录即模块」，深层引用用路径别名（`@/` `@components` `@utils`）消除。

### 3.4 模块化（按业务域）· 可选方案

> 3.2/3.3 是默认基线；当业务组件增多时，**可按业务域模块化作为进阶可选项**。

```text
components/
├── common/        # 跨域原子件（真正全局复用，≤20 个）
├── post/          # 文章域：列表/卡片/元信息/目录
├── player/        # 播放域：播放器+控件+hooks+类型（自包含）
├── settings/      # 设置域
└── layout/        # 页面骨架
```

**三条规则**
1. 只在 ≥ 2 个业务域都用时，才提进 `common/`
2. 域内有复用，就在域内建子目录，不往外推
3. 每个域自带 `hooks/` `types.ts`，自包含不依赖外域

**取舍**：比纯扁平分层更贴合人脑、影响面小；但必须配共享层防重复造轮子。
**触发信号**：组件数 > 80 或某功能目录平铺 100+ 文件时，建议升级为主线。

### 3.5 扁平优先，勿过度嵌套

嵌套 ≤ 3 层；深路径用路径别名消除。

### 3.6 命名即文档

| 类型 | 格式 | 示例 |
|------|------|------|
| UI 组件 | `PascalCase` | `Button` `SearchBar` |
| 容器/模块 | `XxxContainer` / `XxxModule` | `SidebarContainer` |
| 工具函数 | `[功能]-utils` | `content-utils` |
| Hook/Composable | `useXxx` / `useXxx` | `useCalendar` |
| 类型定义 | `[主题]` | `config` `api` |
| 路由 | `[name]` / `[param]` / `[...catch-all]` | `index` `[slug]` |

### 3.7 文档伴随代码

- 目录级 `README.md` 列清组件清单与分类原则
- 复杂组件头部注释（`@description` / `@example` / `@props`）
- 配置入口用表/注释说明每个导出

### 3.8 工程化闭环（可维护性的分水岭）

- `stores/` 管跨组件状态，替代全局事件总线脆弱同步
- `tests/` 覆盖工具与拆分后组件（Vitest / Jest / 框架测试工具）
- CI 自动跑 build + test + lint；锁包管理器（`packageManager` 字段）
- 需要内容/代码分离时，支持独立内容仓库同步

## 四、跨项目取舍速查

| 维度 | 可取范式 | 规避反模式 |
|------|---------|-----------|
| 配置 | 单职责小块 + 索引聚合 | 巨型 config 单点膨胀 |
| 组件 | Atomic Design + 目录即模块 + 桶导出 | 同名组件散落多目录 |
| 类型 | `types/` 或 `utils/types/` 独立子目录 | 全堆进单个文件 |
| 文档 | 目录 README + 配置表 + 头部注释 | 只写代码不写「为何」 |
| 状态 | store 单例 + 依赖注入解 prop drilling | 事件总线满天飞 |
| 复用 | 重复 ≥ 2 次即抽取 | 复制粘贴结构 |
| 测试 | 拆分即补测 | 无测试体系 |
| 分层 | 严格但务实 | 「为分层而分层」硬塞分类 |

## 六、协作约束（强约束 · 前端特有）

> 通用禁令（最小范围、保持一致、禁止炫技等）见 [RootDoc-EngConv.md §八](RootDoc-EngConv.md)。本节仅补充**前端特有的硬性约束**，优先级高于上方"倡导式"准则。任何代码改动、AI 协作均须遵守。
> 若某条无法满足，必须显式说明原因并给出替代方案，不得用"这样更好"这类模糊理由带过。

### 6.1 目录与文件

1. 禁止擅自新建目录、拆分文件、重命名已有模块；新增必须基于现有目录结构放置。
2. 修改前先读取相关现有文件，风格、命名、组织方式必须与现有代码保持一致。
3. 同一功能的代码必须集中在约定位置，禁止为单一功能分散创建多个新文件。

### 6.2 组件

1. 禁止重复创建通用 UI 组件（Button、Input、Modal、Table、Form 等）；必须从项目已有组件库或设计系统中选取。
2. 业务组件必须遵循项目现有封装范式：props 定义、事件命名、状态管理、样式引用方式统一。
3. 禁止把简单组件过度拆分为多个无复用价值的小文件。
4. 组件新增必须说明复用场景；仅在确定会被多处使用时才允许抽离为独立组件（与 2.4「重复 ≥ 2 次」阈值一致）。

### 6.3 代码风格

1. 命名规范：组件文件 `PascalCase`；工具函数 / hook / 常量 `camelCase`；类型 / 接口 `PascalCase`；CSS 类名遵循项目现有约定（BEM / Tailwind / CSS Modules）。（与 3.6 一致）
2. 禁止使用魔法数字、硬编码颜色、硬编码断点，必须使用项目已定义的设计令牌或常量。（与 2.5 设计令牌一致）
3. 禁止在组件中写死样式块；样式必须按项目约定集中管理或使用已有工具类。（与 2.5 一致）
4. 代码必须简洁直接，禁止为炫技引入不必要的抽象或设计模式。

### 6.4 依赖与技术

1. 禁止引入未在 `package.json` 中声明的依赖，或未经评审的新库。
2. 禁止同时使用多种实现同类功能的库。
3. 禁止使用项目已明确弃用的 API、语法或写法。
4. 必须使用项目已选定的框架能力解决问题，不自行封装与框架等价的底层能力。

### 6.5 修改范围（通用约束见 [RootDoc-EngConv.md §八](RootDoc-EngConv.md)）

1. 禁止删除或修改与当前需求无关的现有代码、注释、测试（前端补充：含 `app/` 路由页拆分纪律，详见上方 §3 分层）。
2. 每处修改必须说明理由，不能回答"这样更好"之类的模糊理由（前端补充：组件/样式改动须同步说明对现有设计系统的影响）。

### 6.6 输出要求

1. 先简要列出计划修改的文件和改动点，经确认后再输出具体代码。
2. 输出代码时只输出改动部分或完整文件，禁止输出大段解释性废话。
3. 若某项约束无法满足，必须明确说明原因，并给出替代方案。
