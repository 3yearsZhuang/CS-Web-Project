## 1. 背景与动机：为什么需要统一文档规范

### 1.1 文档体系的角色

项目文档不是装饰性产物，而是**项目的第二代码**。在 CS-Web / CS-Mobile 多仓协作环境中，文档承担以下职责：

1. **新人上手路径**：Onboarding.md 指导新成员在 60 分钟内跑通全栈
2. **跨仓权威指针**：三份 Arch（架构）+ Sec（安全）+ Conv（约定）+ Infra（基础设施）文档是各仓唯一权威
3. **决策历史审计**：ADR（架构决策记录）保留技术选型的权衡与动机
4. **操作手册**：Deploy / Ops 文档指导运维完成部署、回滚、故障处置

### 1.2 治理前的问题画像

在 2026-08-20 治理前，文档体系存在 **4 类结构性问题**，严重影响了文档的可信度和实用性：

| 问题类型 | 严重度 | 核心表现 |
|---|---|---|
| **失准** | 🔴 高 | 全线版本锚定停滞在 0.9.8（实际已 1.0.1·七夕）；存在 `[待填写]` 占位符 |
| **重复** | 🔴 高 | 前端 UI 三件套（UID/UIStandard/UIButton）按钮内容三重重叠；版本号/错误码多处散写 |
| **过度引用** | 🟡 中高 | 每文档头部 4~8 个链接；指路式文档连环跳转 |
| **分散** | 🟡 中 | 根 `docs/` ~15 篇；前端 `tools/docs/` 10 篇；多个单主题小文档 |

这些问题导致了：新成员打开文档时的困惑（"这个版本是真的吗？"）、维护成本的指数级增长（改一处要同步 N 处）、以及知识孤岛的形成（读者不知道该去哪查权威信息）。

## 2. 问题诊断（取证与分析）

### 2.1 失准证据：版本漂移

全线文档版本锚定停滞在 0.9.8，与项目实际版本（1.0.1·七夕，2026-08-19 发布）严重偏离：

| 文档 | 失准内容 |
|---|---|
| `README.md` | 「当前语义版本线：0.9.x（尚未进入 1.0.0）」 |
| `RootDoc-Deploy.md` | 全文多处锚定「0.9.8」 |
| `RootDoc-MigEval.md` | 章节标题「0.9.8 补录」 |
| `Onboarding.md` | `[待填写：确认是否随 1.0.0 注册]` 占位符 |
| `BackDoc-Infra.md` | 断言 Alembic head 为 `d3e4f5a6b7c8`（实际已更新至 `e5f6a7b8c9d0`） |

**根因**：缺乏版本同步机制，每个版本发布后需要手动更新 10+ 文档的版本锚定与 Alembic head。

### 2.2 重复证据：UI 三件套重叠

前端 UI 文档存在三重重叠：

| 文档 | 覆盖内容 | 与其他文档的重叠 |
|---|---|---|
| `FrontDoc-UID.md` | UI 设计规范主文档（按钮/输入框/徽章/Tab/分页/Modal/z-index） | 按钮变体、尺寸、禁止项与 UIButton/UIStandard 重叠 |
| `FrontDoc-UIStandard.md` | 「按钮/输入框/徽章/Tab/分页/Modal/z-index 唯一权威」 | 与 UID 完全重叠（声明 SSOT 但内容重复） |
| `FrontDoc-UIButton.md` | 按钮审计与迁移史 | 按钮的变体、尺寸、禁止项与前两篇重叠 |

**根因**：按主题拆分而非按职责拆分，导致同一内容在多个文档中承载。

### 2.3 过度引用证据：指路式文档

每篇文档头部普遍 4~8 个链接，读者要拼凑完整事实需要跨 3~5 篇文档：

- `Onboarding.md` 附录把禁止事项拆成「→ 见 FrontDoc-03-Conv §12 / FrontDoc-UID §11」
- `FrontDoc-i18n.md` 内多行「剩余待迁移清单已迁移至 `docs/项目待办v2.md`」
- `README.md` 治理规范的「所有权矩阵」本身鼓励"只引用、不重述"，副作用是引用攀高

**根因**：所有权矩阵缺乏层级约束，每个文档的交叉引用数量没有上限。

### 2.4 分散证据：碎片文档

- 前端 `tools/docs/` 10 篇，其中 `capsule-tabs.md`（Tab 配置数据）独立成篇，贡献了碎片
- 根 `docs/` ~15 篇，含调研报告、临时评估、纯索引等
- `FrontDoc-Workbench-ReviewPrompt.md`（prompt 模板）独立成篇

**根因**：按"一个主题一篇文档"组织，而非按"一个职责一个权威"组织。

## 3. 治理策略与执行

### 3.1 治理原则

| 原则 | 说明 |
|---|---|
| **修失准优先** | 低成本高价值，先把版本锚定和占位符修正 |
| **结构收敛** | 合并重复内容（UI 三件套→UID 单一权威），收敛指路式引用（≤2 链接/文档头部） |
| **职责明确** | 每篇文档的 SSOT 权限明确，读者打开即用，不依赖连环跳转 |
| **分类对齐** | Diátaxis 分类（Tutorial/How-to/Reference/Explanation）确保读者预期一致 |

### 3.2 执行计划与结果

| 优先级 | 动作 | 执行结果 |
|---|---|---|
| **P0·修失准** | 2026-08-20 全量版本锚定 0.9.8 → 1.0.1；清 `[待填写]`；Alembic head 校正至 `e5f6a7b8c9d0` | ✅ 完成 |
| **P1·合并 UI** | UIButton+UID+UIStandard → 单一 `FrontDoc-UID.md`；UIButton 审计史并入 CHANGELOG | ✅ 完成 |
| **P2·收敛指路** | i18n 并入 Conv §9；全前端头部「关联」收敛 ≤2；删 `FrontDoc-i18n.md` | ✅ 完成 |
| **P3·归档分散** | `capsule-tabs.md` 并入 UID §4.8 并删；`公共组件调研报告.md` 删除（结论已登记） | ✅ 完成 |

### 3.3 收敛效果

| 仓 | 治理前 | 治理后 | 降幅 |
|---|---|---|---|
| 前端 `tools/docs/` | 10 篇 | **6 篇** | -40% |
| 根 `docs/` | ~15 篇 | ~12 篇 | -20% |
| 后端 `tools/docs/` | 5 篇 | 5 篇 | 0%（已健康） |
| 移动端 `tools/docs/` | 3 篇 | 3 篇 | 0%（已收敛） |

## 4. 结论与展望

### 4.1 当前状态

| 维度 | 状态 | 说明 |
|---|---|---|
| **版本准确性** | ✅ 已修复 | 全线文档锚定 1.0.1·七夕，Alembic head 校正 |
| **内容重复** | ✅ 已消除 | UI 三件套合并为 UID 单一权威，其他重复项并入主文档 |
| **引用密度** | ✅ 已收敛 | 每文档头部链接 ≤2，指路式引用显著减少 |
| **文档分散** | ✅ 已收敛 | 前端从 10 篇降至 6 篇，根 docs 从 ~15 篇降至 ~12 篇 |
| **分类对齐** | 🔄 进行中 | P0-P2 全部完成；P3 Tutorial/How-to + P4 Reference/Explanation 重写中 |

### 4.2 持续治理机制

为防止问题复发，建立以下持续治理机制：

| 机制 | 触发频率 | 负责方 |
|---|---|---|
| **版本同步脚本** | 每次发版 | 根级 `scripts/doc/gen_doc_facts.py` 自动同步 Alembic head / 版本号 |
| **Dead Link 检查** | 每次 CI | `scripts/check/check_dead_links.py` |
| **文档 Review 门禁** | 每次 PR | 检查新增文档的 Diátaxis 分类、SSOT 声明、头部引用数量 |
| **周期性健康检查** | 每月 | 检查版本锚定漂移、引用密度、内容重复 |

### 4.3 一句话结论

> **文档体系已从"多源、失准、重复"的混乱状态收敛为"单一权威、版本准确、结构清晰"的健康状态。P0-P3 治理动作全部落地，后续通过自动化脚本和 CI 门禁防止问题复发。**
